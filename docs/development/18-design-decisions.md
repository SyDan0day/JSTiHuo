## D1/D2 实施补充：顾客 CSRF 恢复与地区标准化

DESIGN_DECISION（2026-10-14）：既定 Order JSON 未携带 CSRF，且无顾客 session GET；首次下单轮换 ORDER Cookie 或页面刷新会失去内存 CSRF。保留既有 JSON 形状，在 redemptionOptions/customerOrder GET 和 redeem 成功响应中增加 X-CSRF-Token 与 X-CSRF-Scope。GET 只轮换同一会话的 CSRF；redeem 成功签发 ORDER WRITE 会话并返回其 CSRF。前端按 ADMIN/PREAUTH/VOUCHER/ORDER 分别保存内存 CSRF，避免管理员与顾客入口互相覆盖。不得持久化 token 到浏览器存储或日志；同键恢复始终先验证持久化会话和凭证版本，再重放订单，当前卡已消费不阻断恢复。

地区使用 [原始开源仓库](https://github.com/modood/Administrative-divisions-of-China) 的 pca-code.json，锁定提交、许可证与 SHA256 于 internal/domain/regions/provenance.json；数据版本为仓库的 2023-06-30 统计数据，不声称是 2026 年最新行政区划。数据随服务版本嵌入，不创建额外数据库表。后续部署更新必须复核父子关系及历史订单；订单把可信地区名称冻结到加密地址内。

原始数据在东莞、中山、儋州、嘉峪关四个不设区城市的第三层为九位镇街统计代码，与 API 的六位区县字段不兼容。实现以规范市级六位代码复用为“全市”第三层，并严格校验所属省、市；镇街填写到详细地址。该适配不伪造县级行政编码，也不丢弃其他省市区数据；禁配仍按省/市/第三层任一级命中拒绝。

## E1 实施补充：订单改期建议与作用域提示

DESIGN_DECISION（2026-10-14）：redemptionCalendar 增加自身 ORDER 会话授权，只允许未回收、截止前的 PENDING 配送订单读取建议。订单修改仍单独要求 WRITE；READ 读取日历不会获得核销或写权限。已有订单继续保留原名额，保持原日编辑不受新配置 blackout/closed 影响；改到新日期必须重新校验完整当前规则、额度和商品预约期限。

订单查询、提权、下单成功和 customerOrder GET 增加 X-Order-Scope 响应头，为界面展示 READ/WRITE 提示，不改变 Order JSON。实际授权仍重查数据库会话及卡凭证版本。Step-up 使用新的 PREAUTH VOUCHER 专用挑战和原 ORDER CSRF，服务端同时验证两个 HttpOnly Cookie，成功撤销旧两种会话。

## E2 实施补充：显式 MOCK 轨迹与人工完成

DESIGN_DECISION（2026-10-14）：MOCK 是显式承运商模式，仅用于自有本地模拟；worker 在发货后三十秒发布模拟运输、六十秒发布模拟签收，固定事件标识保证重试和多 worker 去重。MANUAL 及真实供应商映射目录不运行该模拟。事件正文清楚标注 MOCK，不把模拟状态声称为真实寄送。

人工完成只改变订单终态并审计原因，不把运单改成 DELIVERED 或造签收事件。实际事件独立保留，按发生时间推进当前轨迹，DELIVERED 终态不倒退。顾客轨迹权限来自 ORDER 对象归属，未授权对象返回 404。

`make e2e` 实施为真实 MySQL 的 HTTP/业务服务协议主链，浏览器页面断言仍需 H1。未接入未经授权的轨迹写入口，后续 G2 在可信供应商验签边界之后复用事件服务。

## F1 实施补充：内容发布、列表顺序与初始化

- 复用 catalog 的 Service、事务幂等和审计，内容存取放在独立文件，沿用现有 `content_pages` 表，不追加重复架构或迁移。
- 所有内容编辑采用完整快照与 version；发布、撤下均由 `published` 表达。正文复用服务端 HTML 白名单，不接受属性、URL、图片、脚本或样式；审计只记录引用、版本及发布状态，不保存正文。
- 内容列表固定 ID 降序；`q` 搜索标题/slug；后台 `status` 为 PUBLISHED/DRAFT/空，公开仅 PUBLISHED/空。首页从最新 100 条已发布内容中按 `sort_order` 升序展示推荐及至多四条公告，不改变列表游标合同。
- 不自动发布未经运营确认的商家介绍与联系方式。`guide/about/contact/notice` 为固定信息入口；未发布与撤下均返回 404 并显示明确空态。自有说明和合成商品仅在隔离浏览器夹具中生成，不进入业务库。
- 推荐由用户手动切换，避免自动播放打断阅读。信息页与商品页路由参数变化重新请求，并防止旧响应覆盖；后台保存结果不确定时冻结快照，以原幂等键和原正文确认。


## F2–G3 实施补充：隐私、异步结果与运营边界

- 反馈、任务和运营写命令的幂等表只存对象 ID 与请求 HMAC；重放重新读取授权资源，不能缓存反馈正文、临时密码、联系人或文件字节。
- 导入上传采用与代理限额一致的 5 MiB；报表输出上限单独为 10 MiB。任务来源权限、所有者及管理员认证版本在 worker 执行前重查。
- 售后读取权限统一为 `after_sale.read`；旧目录键 `aftersale.read` 仅保留兼容记录，不授权新接口。Job 公开增加可选 order_id/carrier_id/tracking_no，方便确认实际面单，不暴露内部 options。
- 未分类外部调用错误按 UNKNOWN 保守处理；只有明确未执行的拒绝或暂时失败才能解除锁或重试。通知最多五次调用，失败一至四次分别等待 1m/5m/30m/2h，第五次进入 DEAD；原规格列出的 12h 不再用于第六次调用。
- 供应商自由轨迹描述不进入公开库，事件类型映射固定中文文案；供应商事件 ID 按 provider 摘要后与运单联合去重。MOCK 始终显式标记模拟。
- 角色和账户变更均需近期复核，identity_guard 串行化最后管理员检查；现有和请求权限都不能超出操作者当前上限，改权同时递增 auth_version 并撤销会话。
- 日历配置允许最少提前零天，与 OpenAPI 及 BR05 参数化公式一致；缺省仍为一天。兑换/改期取得日历锁后以 READ COMMITTED 无锁重读规则，避免配置竞态和反向配置锁。更新配置预建未来 31 天日历，降低容量不得小于已有占用。
- 公开二维码仅编码当前 origin 和固定公开路径，使用锁定的 qrcode 依赖在浏览器本地完成；没有任意 URL、卡密或令牌输入入口。

## H1/H2 实施补充：性能、恢复与运行隐私

- 订单列表在只读一致快照中批量读取商品，消除每单额外查询；兑换先共享锁批次，再仅锁目标卡，避免 JOIN 让同批次不同卡排他串行。原有事务原子性、卡券唯一消费及配置复查不变，无新增业务 DDL。
- 备份采用独立 AES-256-GCM 密钥、随机 nonce、有版本的 tar 白名单，完整认证后才发布 SQL 和公开图片。单包含头最多 512 MiB，当前为有界内存工具；不备份私有卡密、导入源及报表字节。密钥和历史 PII 版本分开保管。
- 恢复到新库和新卷，精确库名确认后原子撤销会话、过期私有文件、封存 GENERATED 批次并隔离不确定面单/通知。审计失败整体回滚；不自动补库存或回退订单。PII 验证使用二进制引用列，避免连接字符集引发 UNION 排序规则冲突。
- 生产配置为显式 HTTPS overlay，API/worker 降权 UID 10001，代理 UID 101，私钥目录避开 `/var/run` tmpfs。可信代理 CIDR 显式配置，入口覆盖客户端 IP；应用和代理日志不记录 URI、查询或正文。
- 完成超过保留期（默认 180 天）的订单每小时最多清理 1000 单；活动 OPEN/APPROVED 售后暂停。逐单与案件共用订单锁，收件密文替换为受认证的空快照，手机索引置 32 字节零值作为清理标记，清空订单备注、撤销本单会话并留只含对象 ID 的审计。保留商品、状态和账本；已清理订单禁止新建售后，避免无收件资料时批准补发。保留期环境配置只允许 180–36500 天。
- RPO/RTO 报告区分小样本实测、持续备份调度和生产规模：本地指定 binlog 点可无损恢复，不代表已部署异机副本或满足任意规模 SLA。真实供应商、生产证书和生产发布另行验收。
