# 20 编程Agent执行指南

本套为持续维护的实施规格；A1–H2 本地实现与验收已交付，实际状态见 IMPLEMENTATION-STATUS.md 和各包记录。先读00→01→18→03/04/05，再按所接工作包读07–14；schema.sql、openapi.yaml与15是具体实现合同。原站事实只用01的E证据，所有未知已由ADR确定默认，不以再次确认所有规则为开工门槛。

## 每次接包步骤

1. 查看项目树/git status/AGENTS 与最新交付记录；保留已有改动，核实现有代码和服务，不沿用规格起草时的空工程假设。
2. 定位17工作包ID，核对前置包确实通过验收；记录依赖commit/契约版本。
3. 从19追踪需求→页面→operationId→Service事务→数据表→测试；先列本包更改范围。
4. 先迁移/领域规则与集成测试，再Service/API，最后Vue交互；不能只做页面mock。
5. 采用固定Clock/随机源接口的本地合成数据，所有供应商MOCK，禁用真实通知。不调用目标演示站业务接口。
6. 执行本包测试并校验OpenAPI类型同步；修改schema字段必须同步DDL、API、前端类型、ADR与测试。
7. 输出实际执行命令和结果，不能把“测试设计”称“测试通过”；静态校验不能替代真实 MySQL、浏览器和恢复验收。

## 代码约束

Handler不处理复杂业务、不直连数据库；Service事务统一sql.Tx；Repository只存取；所有输入服务端验证；写操作权限/CSRF/幂等/审计缺一不可。禁止新增通用任意状态PATCH或任意SQL查询/配置接口。采用唯一约束而非只靠按钮disabled防重复。PII/secret不进日志/URL/仓库。

## 冲突处置

事实冲突优先NETWORK/LIVE，再SOURCE，最后PROTOTYPE。新业务默认以已采纳ADR为准；不能因原型能点或旧报告UNKNOWN撤回已明确的自主设计。发现不可实施细节时直接做最小安全修订并记录ADR补充，保留原证据。关键不变量（单卡单消费、库存非负、审计、原发唯一）不得无说明放宽。

API错误、状态转换、库存语义的权威顺序：03/04/05/13业务→08 DDL与09 OpenAPI（必须保持一致）；如果文本和机器合同矛盾，先一起修复，不任意选择较易一边。18负责解释选择理由而非另一套默认。

## 完成定义

完成工作包=数据库持久化+真实API+Vue入口+权限/异常+所列测试通过+必要文档更新；完整v1=H1/H2通过。发布前还需真实MySQL执行迁移、性能/备份演练、生产密钥/内容/域名及可用供应商；这些不阻止本地开发，但不能被MOCK证明取代。

后续开发以已交付 A1–H2 为基线，只接明确变更；D2 等核心事务仍须严格并发回归。无需等待原站新增权限恢复再开始自有实现。
